# Security Policy

## Supported versions

| Version | Supported |
|---|---|
| `main` | ✅ |
| 0.1.x | ⚠️ pre-release; fixes land on `main` only |

`acronymkit` has not reached 1.0. Until it does, security fixes are applied to `main` and released in
the next version rather than backported.

## Reporting a vulnerability

Please report privately via
[GitHub Security Advisories](https://github.com/pierce-lonergan/AcronymKit/security/advisories/new).
Do not open a public issue for an unpatched vulnerability.

Expect an acknowledgement within 7 days and an assessment within 14. If a fix is warranted, you will
be credited in the advisory unless you ask otherwise.

## Threat model

`acronymkit` parses untrusted text. The realistic risks from that text are therefore denial of
service and resource exhaustion, not code execution:

- **Algorithmic complexity attacks.** A crafted document that makes extraction or generation
  superlinear. One such defect has already been found and fixed (a nested-bracket path that took 43 s
  on a 112 KB document). Reports of new ones are in scope and welcome.
- **Unbounded memory.** Inputs that make the candidate search or the token stream grow without limit.
  `Config.max_search_nodes`, `search_beam_width` and `search_time_budget_ms` exist to bound this; a
  way around them is a bug.
- **Catastrophic regex backtracking** in the tokenizer or extractor patterns.

## What the library does not do, stated exactly

This section used to read: "the library performs no network I/O, executes no user-supplied code,
and writes no files." The first clause holds. The other two are true only with qualifications, and
an absolute that has exceptions gets the whole document discounted the moment a reader finds one.

**No network I/O — holds, and is tested.** No module in the package contains a call to a network
primitive, and the test suite passes with every socket primitive patched to raise. A network
request originating in `acronymkit` would be a defect; reports of one are in scope.
`tools/fetch_data.py` does download pinned assets, but it is a maintainer tool, is not importable
from the package, and verifies every download against a SHA-256 recorded in the source.

**No execution of caller-supplied input — but third-party code does run.** Nothing a caller passes
in is compiled, evaluated or deserialised into code; input text is data from end to end. Code
supplied by the *environment* is a different question, and it executes on the default path.
`pydantic` scans the `pydantic` entry-point group and imports whatever is advertised there while
building a model — which is what constructing an `acronymkit.Config` does. The import has already
happened by the time any `acronymkit` code runs, so the library can detect it and cannot prevent
it: `acronymkit.capabilities()` reports installed plugins, `acronymkit doctor --offline` exits
non-zero when any is present, and under `ACRONYMKIT_OFFLINE=1` a `Config()` built in a process that
has one loaded raises `OfflineError` rather than continue under a promise already broken. The
prevention is `PYDANTIC_DISABLE_PLUGINS=1` in the environment. We document it instead of setting
it, because setting it would mutate global state shared with every other `pydantic` user in the
process.

**Two filesystem writes, both to a path the caller named.** `PrecisionTable.save()` in
`acronymkit._pseudo_precision` writes JSON to the path its caller passes in.
`acronymkit.resources.resource_path()` calls `importlib.resources.as_file`, which materialises a
temporary file when the package is loaded from a zip; an ordinary unzipped install returns the real
resource path and writes nothing, and no code inside the package calls it. Nothing in the library
chooses a write location for itself, and nothing writes on import, extraction or generation.

So what is out of scope is narrower than the old sentence implied. `acronymkit` fetching a URL,
executing something a caller passed in, or writing to a path nobody named would each be a defect
and each is worth reporting. The `pydantic` plugin mechanism is not: it is upstream's design, we
cannot disable it from inside the process, and it is described here so an operator can decide about
it rather than discover it.

## Supply chain

- All GitHub Actions are pinned to commit SHAs, not tags.
- Workflows run with `contents: read` unless a job explicitly needs more.
- Publishing uses PyPI Trusted Publishing (OIDC); no long-lived token is stored in the repository.
- Dependabot monitors `pip` and `github-actions`.
- Third-party data assets are pinned and checksummed. The ledger is
  [`data/LICENSES.md`](data/LICENSES.md), generated by `tools/fetch_data.py --write-ledger`; the
  link is repository-relative. The wheel contains `acronymkit/` and its `.dist-info` metadata and
  nothing else — no `data/` directory — so a reader holding only a wheel cannot follow it. For
  them, the attribution for each vendored asset travels in the header of the resource file derived
  from it (see the SCOWL notice at the top of `lexicon_en.txt`).
